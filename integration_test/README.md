# Integration Tests

## 概要

この文書は、このプロジェクトの結合テストに関して説明しています。

## 用語

|単語|定義|
|-|-|
|受け入れテスト|ソフトウェアの状態がユーザーストーリーを満足するものであることを検証する目的で作成された結合テスト|
|Firebase結合テスト|Firebaseとの相互作用を検証する目的で作成された結合テスト|

## 目的

結合テストを実施する目的は以下のとおりです。

- ソフトウェアの状態がユーザーストーリーを満足するものであることを確かめるため
  - この目的で作成された結合テストを**受け入れテスト**と呼びます
  - 手作業によるデグレ確認作業の削減、および新規ユーザーストーリー開発時に受け入れ基準を満たしているかの判断が可能になります
- Firebaseとの相互作用をテストするため
  - この目的で作成された結合テストを**Firebase結合テスト**と呼びます
  - 単体テストでFirebaseのシステムをモックしたテストに価値を感じないため、Firebase local emulatorと接続した状態で検証を行います

## 受け入れテスト

### 受け入れテストの実行方法

まず、前提条件として以下が必要です。

- Android device emulatorが起動していること
- Firebase CLIがインストールされていること（Firebase local emulatorの設定は同一リポジトリの`firebase/`ディレクトリにあります）

受け入れテストは以下のコマンドで実行できます。

```shell
# Firebaseの設定ディレクトリへ移動（リポジトリルートから）
cd firebase
# Firebase local emulatorの起動と受け入れテストの実行
firebase emulators:exec \
--project household-accounts-1129d \
--only auth,firestore,functions \
--import ../integration_test/saved-data \
../integration_test/run.sh
```

`--project`の指定は必須である。`firebase/.firebaserc`には`default`エイリアスが存在しないため、
`--project`を省略すると`firebase emulators:exec`は`demo-no-project`という別プロジェクトIDでCloud Functionsエミュレータを起動してしまう。
一方、アプリ（`lib/firebase_options.dart`）は常に`household-accounts-1129d`でFirestoreエミュレータに接続するため、
両者のプロジェクトIDが食い違うと、サインアップ時に`onCreateUser`トリガーが作成するドキュメント（`privateProfiles`等）が
アプリから見えなくなり、ダッシュボードがローディング状態のまま止まってしまう。

毎回このコマンドを打たなくていいように、`.vscode/tasks.json`に`integration test`というタスクを定義しています。
VSCodeの場合、このタスクを実行すれば上記のコマンドが走ります。
ただし、この場合も前提条件が満たされているかの確認は別途必要です。

### 受け入れテストのファイル構成

受け入れテストの起点は`integration_test.dart`です。
このファイル自体には受け入れテストはひとつも実装されていません。
受けれテストの実装は`*_feature_test.dart`にあります。
`integration_test.dart`から`*_feature_test.dart`に実装されたテストが呼び出されます。

### 受け入れテストの名前

ユーザーストーリーを意識した名前になっています。
つまり、`[ペルソナ]は、[システムが提供する機能]ができるので、[得られる価値]を得ることができる`というフォーマットを意識しています。

これにより、受け入れテストが想定している**ペルソナ、機能、価値**が明らかになります。

### 受け入れテストが作成されるユーザーストーリー

すべてのユーザーストーリーに対して受け入れテストが作成されているわけではありません。
システムの正常系の振る舞いに関する受け入れテストが作成されています。
例えば、以下の例であれば1のユーザーストーリーに対する受け入れテストは作成されますが2に対するものは作成されません。
受け入れテストで異常系を再現するのが難しいことが主な理由です。

```text
1. ユーザーは、カテゴリを作成できるので、レコードをカテゴリ別に管理することができる。
2. ユーザーは、カテゴリ作成でエラーが発生したときその旨を知ることができるので、再度カテゴリ作成を試みることができる。
```

また、あるユーザーストーリーAが別のユーザーストーリーBを内包する場合、Bに関する受け入れテストは作成されません。
例えば、以下の例であれば1のユーザーストーリーに対する受け入れテストは作成されますが2に対するものは作成されません。
2の内容は1に関する受け入れテストでも検証できていることが理由です。

```text
1. ユーザーは、作成済みのカテゴリの名前を変えることができるので、誤ってカテゴリを作成しても安心できる。
2. ユーザーは、作成済みのカテゴリの名前を確認できるので、誤ってカテゴリを作成していないか判別できる。
```
